# StockPulse Frontend — Merchandising Intelligence Dashboard

The StockPulse frontend is a high-performance single-page merchandising dashboard built with React 18, TypeScript, and Vite. It provides retail operators and merchandisers with real-time visibility into inventory levels, sales velocity, low-stock warnings, and dynamic pricing or replenishment recommendations generated by the backend's AI and rule engines.

---

## Tech Stack

The frontend application uses modern, lightweight dependencies without heavy UI frameworks:

- **Core Framework**: React `18.3.1` (Hooks, functional components)
- **Language**: TypeScript `5.6.2` (Strict type safety, complete domain interfaces)
- **Build & Dev Server**: Vite `5.4.14` (Ultra-fast Hot Module Replacement)
- **Styling**: Vanilla CSS with CSS Custom Properties (Dark theme, glassmorphic accents, responsive grid)
- **HTTP Client**: Native browser `fetch()` wrapped in a strongly typed API module (`src/api.ts`)
- **Linting**: ESLint `9.15.0`

## Frontend Architecture

The application adopts a unidirectional data-flow architecture with a centralized API communication boundary:

```
┌────────────────────────────────────────────────────────┐
│                      App Component                     │
│  (State: products, pricingSuggestions, reorderSuggestions, │
│          stockInputs, actionLoading, polling loop)     │
└───────────┬────────────────────────────────▲───────────┘
            │ Triggers actions / polls       │ State updates
            ▼                                │
┌────────────────────────────────────────────────────────┐
│                   API Module (api.ts)                  │
│       (Centralized REST fetch calls & error handling)  │
└───────────┬────────────────────────────────▲───────────┘
            │ HTTP Requests                  │ JSON Responses
            ▼                                │
┌────────────────────────────────────────────────────────┐
│            Backend REST Endpoints (port 8080)          │
│   (/products, /pricing-suggestions, /reorder-suggestions)│
└────────────────────────────────────────────────────────┘
```

### Why API Calls are Centralized
All network transport is consolidated within [src/api.ts](file:///c:/Users/poweroot/Desktop/zycus-hackathon/zycus-hackathon/frontend/src/api.ts). This offers several architectural benefits:
- **Separation of Concerns**: UI components remain declarative and focus strictly on rendering and user interaction, remaining agnostic of HTTP transport details.
- **Single Source of Truth**: Backend URL configurations, HTTP headers (`Content-Type: application/json`), and status code verification (`response.ok`) are configured once.
- **Type Safety**: API functions enforce strict parameter and return types matching [src/types.ts](file:///c:/Users/poweroot/Desktop/zycus-hackathon/zycus-hackathon/frontend/src/types.ts).
- **Graceful Error Handling**: Non-standard response formats or missing data are caught and mapped into human-readable exceptions before reaching React state.

## Actual REST API Endpoints Used

The frontend interacts with the following backend endpoints:

| Method | Endpoint Path | Purpose | Request Payload | Response & UI Usage |
|--------|---------------|---------|-----------------|---------------------|
| `GET` | `/products` | Fetches the full product catalog | None | Populates product cards, metric badges (price, stock/threshold, demand velocity), and summary counters. |
| `POST` | `/products/{id}/orders` | Simulates a customer sale | `{"quantity": 1}` | Decrements product stock, increases demand velocity by `+1.0`, triggers backend agentic event, initiates UI polling. |
| `PATCH` | `/products/{id}/stock` | Manually updates inventory | `{"stockLevel": <number>}` | Overwrites stock level, triggers `InventoryLowEvent` if below reorder threshold, initiates UI polling. |
| `GET` | `/pricing-suggestions/products/{id}` | Fetches pricing recommendations | None | Retrieves all pricing suggestions for product. Frontend filters for `status === 'PENDING'` to render approval cards. |
| `GET` | `/reorder-suggestions/products/{id}` | Fetches reorder recommendations | None | Retrieves all reorder suggestions for product. Frontend filters for `status === 'PENDING'` to render approval cards. |
| `PATCH` | `/pricing-suggestions/{id}` | Approves or rejects pricing | `{"status": "ACCEPTED" \| "REJECTED"}` | Updates suggestion status. When `ACCEPTED`, product price updates immediately and status resets to `ACTIVE`. |
| `PATCH` | `/reorder-suggestions/{id}` | Approves or rejects reorder | `{"status": "ACCEPTED" \| "REJECTED"}` | Updates suggestion status. When `ACCEPTED`, recommended quantity is credited to product stock level. |

## UI Flow & Lifecycle

```
1. Initial Load
   └─► App mounts ──► calls loadData() ──► fetches GET /products and suggestions for each product
       └─► Computes summary counts (Total Products, Low Stock count, Pending Suggestions)

2. User Mutation
   └─► User clicks "Simulate Sale" or enters stock and clicks "Set Stock"
       └─► Disables action button & displays loading state (actionLoading[id] = true)
       └─► Submits mutation to backend (POST /orders or PATCH /stock)

3. Agentic Polling
   └─► Mutation succeeds ──► startPolling(productId) triggers every 2,000ms
       └─► Continues checking for new PENDING recommendations up to 5 attempts (10 seconds)
       └─► As soon as a PENDING suggestion appears, polling terminates early and refreshes catalog

4. Human Checkpoint
   └─► Card renders pending suggestion with recommended value, direction, and trigger badge
   └─► User clicks "Accept" or "Reject"
   └─► Backend updates state and frontend automatically reloads to reflect updated price or stock
```

## Agentic Polling Mechanism

Because the backend utilizes asynchronous event listeners (`@Async`) and external AI inference (LiteLLM) to generate suggestions, suggestions are not returned synchronously within the sale simulation response.

### Implementation Details ([src/App.tsx](file:///c:/Users/poweroot/Desktop/zycus-hackathon/zycus-hackathon/frontend/src/App.tsx#L51-L77))
- **Interval**: Runs every **2,000 milliseconds (2 seconds)**.
- **Maximum Attempts**: **5 iterations** (10-second timeout window).
- **Early Termination**: Immediately clears the timer interval if any suggestion (`pricing` or `reorder`) with status `PENDING` is detected.
- **Post-Poll Synchronization**: When a pending suggestion is discovered, `api.getProducts()` is called to synchronize product statuses (e.g. `PRICE_REVIEW_PENDING`).

## Step-by-Step Demo Walkthrough

### 1. Inventory-Low Demo
1. Ensure both backend and frontend are running.
2. Locate **PRD-003** (*Organic Cotton T-Shirt*). Note stock is `8` and threshold is `15`.
3. In the "Qty" input, enter `4` and click **Set Stock**.
4. The backend processes the stock update and detects `stockLevel < reorderThreshold`.
5. Within 2–4 seconds, the pending suggestions appear directly inside the PRD-003 card:
   - **💡 Pricing Suggestion**: Recommends increasing the price by +10% ($27.49).
   - **📦 Reorder Suggestion**: Recommends restocking +41 units with 7 days lead time.

### 2. Demand-Spike Demo
1. Locate **PRD-008** (*Hoodie - Heather Grey*).
2. Click **🛒 Simulate Sale**.
3. Stock drops to `10` and demand velocity increases to `16.0/day` (well over 3× the apparel category average).
4. The background agent detects the demand spike and presents tailored pricing and replenishment suggestions with reasoning.

### 3. Pricing Approval
1. On any card displaying a **💡 Pricing Suggestion**, click the green **Accept** button.
2. The UI dispatches `PATCH /pricing-suggestions/{id}` with `{"status": "ACCEPTED"}`.
3. Upon success, the dashboard refreshes:
   - The suggestion card disappears.
   - The product's **Price** metric updates to the newly recommended price.
   - The product status resets to `ACTIVE`.

### 4. Reorder Approval
1. On any card displaying a **📦 Reorder Suggestion**, click the green **Accept** button.
2. The UI dispatches `PATCH /reorder-suggestions/{id}` with `{"status": "ACCEPTED"}`.
3. Upon success:
   - The suggestion card disappears.
   - The product's **Stock / Threshold** metric immediately increases by the recommended quantity.

## Current Implementation Limitations

- **Polling vs. Real-time Streams**: The frontend uses client-side interval polling (2s interval, max 5 attempts) to check for async suggestions rather than Server-Sent Events (SSE) or WebSockets.
- **Single Page View**: Operates as a single unified dashboard without client-side routing (React Router is not installed).
- **Authentication**: There is no login, JWT validation, or role-based permission system implemented.
- **Charts / Visualizations**: Analytics and metrics are rendered using structured metric cards and badges rather than third-party canvas or SVG graphing libraries (e.g. Chart.js, Recharts).
